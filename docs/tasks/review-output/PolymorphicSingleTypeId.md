# PolymorphicSingleTypeId Review

## Verdict
Not functionally correct. The generated code round-trips homogeneous non-empty `List<Animal>` payloads, but it does not honor `TypeIdProperty = nameof(AnimalTypeId)` from [input.cs](/C:/Users/Jonas/repos/private/JKamsker/FourSer.Gen/tests/FourSer.Tests/GeneratorTestCases/PolymorphicSingleTypeId/input.cs#L8). On serialize, it derives the discriminator from `Animals` and hard-codes `1` for empty or `null` collections instead of using `obj.AnimalTypeId`, which conflicts with the public contract that `SingleTypeId` is determined by the referenced property ([PolymorphicMode.cs](/C:/Users/Jonas/repos/private/JKamsker/FourSer.Gen/src/FourSer.Contracts/PolymorphicMode.cs#L12), [SerializeCollectionAttribute.cs](/C:/Users/Jonas/repos/private/JKamsker/FourSer.Gen/src/FourSer.Contracts/SerializeCollectionAttribute.cs#L36)).

## Open questions / assumptions
- Assuming the contract comments are authoritative, `TypeIdProperty` should control the discriminator value for `SingleTypeId` collections, including empty collections, rather than being overwritten from the collection contents.
- I did not find another material correctness issue in the generated `Cat`, `Dog`, or `Animal` serializers for this specific test case.
- Local execution could not fully verify the snapshot tests because `dotnet test tests/FourSer.Tests/FourSer.Tests.csproj --filter PolymorphicSingleTypeId` builds but the test host cannot start without `Microsoft.NETCore.App 9.0.0`.
