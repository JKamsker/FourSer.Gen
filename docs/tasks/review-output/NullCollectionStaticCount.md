# NullCollectionStaticCount Review

## Verdict
Functionally correct for FourSer's current collection contract. The generated code accepts a `null` `Items` collection, encodes it as count `0`, and deserializes zero-count payloads to an empty `List<Item>` (`tests/FourSer.Tests/GeneratorTestCases/NullCollectionStaticCount/NullCollectionStaticCount.RunGeneratorTest.verified.txt:115`, `tests/FourSer.Tests/GeneratorTestCases/NullCollectionStaticCount/NullCollectionStaticCount.RunGeneratorTest.verified.txt:177`, `tests/FourSer.Tests/GeneratorTestCases/NullCollectionStaticCount/NullCollectionStaticCount.RunGeneratorTest.verified.txt:141`). That matches the current collection behavior covered elsewhere in the test suite (`tests/FourSer.Tests.Behavioural/Collections/CollectionTests.cs:97-109`, `tests/FourSer.Tests/OptimizationCollectionFailureTests.cs:101-145`). The static-count part is also correct: sizing reserves one fixed `int` count prefix and does not introduce extra validation bookkeeping (`tests/FourSer.Tests/GeneratorTestCases/NullCollectionStaticCount/NullCollectionStaticCount.RunGeneratorTest.verified.txt:114`).

The main expectation caveat is that `Items` is declared non-nullable in a nullable-enabled project (`Directory.Build.props:5`, `tests/FourSer.Tests/GeneratorTestCases/NullCollectionStaticCount/input.cs:16`), but the generated code still treats it as optional.

## Findings
1. Low: The generated serializer ignores the source nullability contract for `Items`. `tests/FourSer.Tests/GeneratorTestCases/NullCollectionStaticCount/input.cs:16` declares `List<Item> Items` in a nullable-enabled project, but the generated code accepts `null` in sizing and serialization (`tests/FourSer.Tests/GeneratorTestCases/NullCollectionStaticCount/NullCollectionStaticCount.RunGeneratorTest.verified.txt:115-125`, `tests/FourSer.Tests/GeneratorTestCases/NullCollectionStaticCount/NullCollectionStaticCount.RunGeneratorTest.verified.txt:177-180`, `tests/FourSer.Tests/GeneratorTestCases/NullCollectionStaticCount/NullCollectionStaticCount.RunGeneratorTest.verified.txt:206-209`) and always materializes a non-null `List<Item>` on deserialize (`tests/FourSer.Tests/GeneratorTestCases/NullCollectionStaticCount/NullCollectionStaticCount.RunGeneratorTest.verified.txt:141-149`, `tests/FourSer.Tests/GeneratorTestCases/NullCollectionStaticCount/NullCollectionStaticCount.RunGeneratorTest.verified.txt:159-168`). This matches current collection handling for nullable lists (`tests/FourSer.Tests.Behavioural/Collections/CollectionTests.cs:97-109`) and the generator's `List<T>` metadata (`src/FourSer.Gen/TypeInfoProvider.cs:239-250`), so it is not a functional regression, but it is likely surprising for users who read the member as required.
2. Info: The verification artifact contains duplicate `// <auto-generated/>` banners and repeated `using` / alias blocks at `tests/FourSer.Tests/GeneratorTestCases/NullCollectionStaticCount/NullCollectionStaticCount.RunGeneratorTest.verified.txt:1-15` and `tests/FourSer.Tests/GeneratorTestCases/NullCollectionStaticCount/NullCollectionStaticCount.RunGeneratorTest.verified.txt:87-101`. `tests/FourSer.Tests/GeneratorTests.cs:78-83` concatenates multiple generated `*.g.cs` files into one snapshot, so this is snapshot noise rather than a functional issue in a single emitted source file.
3. Info: Both deserializers include redundant `checked((int)itemsCount)` casts and extra one-shot temporaries in `tests/FourSer.Tests/GeneratorTestCases/NullCollectionStaticCount/NullCollectionStaticCount.RunGeneratorTest.verified.txt:141-149` and `tests/FourSer.Tests/GeneratorTestCases/NullCollectionStaticCount/NullCollectionStaticCount.RunGeneratorTest.verified.txt:159-168`. `itemsCount` is already an `int`, so those casts do not add overflow protection for this case.

## Performance opportunities
- Stream collection IO is still per-element. `MainObject.Deserialize(stream)` and `Serialize(obj, stream)` delegate once per item (`tests/FourSer.Tests/GeneratorTestCases/NullCollectionStaticCount/NullCollectionStaticCount.RunGeneratorTest.verified.txt:164`, `tests/FourSer.Tests/GeneratorTestCases/NullCollectionStaticCount/NullCollectionStaticCount.RunGeneratorTest.verified.txt:219`), and each `Item` stream method reduces to a single 4-byte primitive read/write (`tests/FourSer.Tests/GeneratorTestCases/NullCollectionStaticCount/NullCollectionStaticCount.RunGeneratorTest.verified.txt:57`, `tests/FourSer.Tests/GeneratorTestCases/NullCollectionStaticCount/NullCollectionStaticCount.RunGeneratorTest.verified.txt:82`). Because `Item` is fixed-width (`tests/FourSer.Tests/GeneratorTestCases/NullCollectionStaticCount/NullCollectionStaticCount.RunGeneratorTest.verified.txt:27-29`), a future buffered collection path could reduce O(n) tiny stream operations to one bulk read/write plus in-memory processing.
- Collection sizing and serialization duplicate element null guards before calling `Item.GetPacketSize` / `Item.Serialize`, and those delegated methods immediately perform their own root-null guards again (`tests/FourSer.Tests/GeneratorTestCases/NullCollectionStaticCount/NullCollectionStaticCount.RunGeneratorTest.verified.txt:119-123` with `tests/FourSer.Tests/GeneratorTestCases/NullCollectionStaticCount/NullCollectionStaticCount.RunGeneratorTest.verified.txt:21-29`, `tests/FourSer.Tests/GeneratorTestCases/NullCollectionStaticCount/NullCollectionStaticCount.RunGeneratorTest.verified.txt:186-190` with `tests/FourSer.Tests/GeneratorTestCases/NullCollectionStaticCount/NullCollectionStaticCount.RunGeneratorTest.verified.txt:62-69`, `tests/FourSer.Tests/GeneratorTestCases/NullCollectionStaticCount/NullCollectionStaticCount.RunGeneratorTest.verified.txt:215-219` with `tests/FourSer.Tests/GeneratorTestCases/NullCollectionStaticCount/NullCollectionStaticCount.RunGeneratorTest.verified.txt:76-82`). An internal trusted-non-null path could remove one branch per element.
- No major span batching gap is apparent beyond that. `Item` is a reference type, so the unmanaged `CollectionsMarshal` bulk path used for primitive lists does not apply directly here.

## Open questions / assumptions
- Assuming this case is meant to validate the current "null collection serializes as zero count and round-trips as empty" behavior, the snapshot is correct.
- If the intent was to honor the source nullability contract in `tests/FourSer.Tests/GeneratorTestCases/NullCollectionStaticCount/input.cs:16`, this test case should probably either declare `Items` as `List<Item>?` or use an explicit null-preserving encoding mode that distinguishes `null` from empty.
