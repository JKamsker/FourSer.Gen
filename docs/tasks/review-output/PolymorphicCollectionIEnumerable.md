# PolymorphicCollectionIEnumerable Review

## Verdict
Mostly correct for round-tripping homogeneous `IEnumerable<Item>` values on span and seekable-stream paths, but not fully aligned with likely user expectations. The main issue is that the generated `Serialize(Stream)` path unnecessarily requires a seekable stream even though the enumerable is eagerly buffered first; there is also a lower-severity surprise around nullability and implicit default-discriminator handling for empty or `null` collections.

## Findings
1. Medium: `Serialize(Stream)` is more restrictive than necessary and will fail on non-seekable writable streams. `tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionIEnumerable/PolymorphicCollectionIEnumerable.RunGeneratorTest.verified.txt:273-325` eagerly materializes `obj.Items` into `itemsValidatedItems = Enumerable.ToList(obj.Items)`, so the item count is already known before any bytes are written. Despite that, `:312-317` still enforces `stream.CanSeek`, writes a placeholder count, and later seeks back to patch it at `:373-376`. For this `IEnumerable<Item>` case the generated stream serializer could write `itemsValidatedItems.Count` up front and stream directly to sockets, pipes, and other non-seekable streams. That restriction is not implied by `tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionIEnumerable/input.cs:9-13`, so it is a likely behavior gap for users.
2. Low: The non-nullable `Items` member is still treated as optional, and empty or `null` values silently use the first polymorphic option as the discriminator. `tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionIEnumerable/input.cs:9-13` declares `IEnumerable<Item> Items` without `?` and without an explicit default `[PolymorphicOption(..., isDefault: true)]`, but the generated serializer accepts `null` and empty collections, writing type id `10` at `tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionIEnumerable/PolymorphicCollectionIEnumerable.RunGeneratorTest.verified.txt:200-203`, `:210-223`, `:318-320`, and `:327-339`, then always deserializes to a non-null `List<Item>` at `:68-70`, `:103-104`, `:114-116`, and `:149-150`. That fallback is internally consistent with `src/FourSer.Gen/CodeGenerators/Core/PolymorphicUtilities.cs:9-38`, which uses `options[0]` when no explicit default is marked, but it is still likely surprising from the source model alone.
3. Info: The snapshot contains substantial duplicate generated logic and noise. The span and stream serializers repeat the same first-item discriminator resolution and per-item validation logic almost verbatim at `tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionIEnumerable/PolymorphicCollectionIEnumerable.RunGeneratorTest.verified.txt:159-196` and `:273-310`, then recompute the discriminator again for the write switch at `:216-256` and `:332-372`. The concatenated snapshot also repeats identical prologue blocks and nearly identical zero-member serializers for `Item`, `Sword`, `Shield`, and `Potion` at `:383-676`. This is not a correctness issue, but it is redundant generated code.

## Performance opportunities
- Since `itemsValidatedItems` is already a `List<Item>` in both serializers at `tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionIEnumerable/PolymorphicCollectionIEnumerable.RunGeneratorTest.verified.txt:159` and `:273`, write `itemsValidatedItems.Count` directly instead of reserving and backpatching the count. On the stream path that would also remove the `CanSeek` requirement, two position changes, and one extra count write.
- Reuse the validated discriminator from the prepass instead of recomputing it from `itemsEnumerator.Current` in `tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionIEnumerable/PolymorphicCollectionIEnumerable.RunGeneratorTest.verified.txt:216-223` and `:332-339`.
- Replace `itemsValidatedItems?.Count() ?? 0` in `tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionIEnumerable/PolymorphicCollectionIEnumerable.RunGeneratorTest.verified.txt:160` and `:274` with the list's `Count` property to avoid needless LINQ dispatch.
- `GetPacketSize` materializes the enumerable to an array and walks it at `tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionIEnumerable/PolymorphicCollectionIEnumerable.RunGeneratorTest.verified.txt:29-53`, while `Serialize` materializes it to a list and revalidates or walks it again at `:159-257` and `:273-378`. That is mostly an API-shape cost for pure `IEnumerable<T>` members, but it is the main remaining allocation and CPU overhead in this case.

## Open questions / assumptions
- Assuming current intended behavior is that `SingleTypeId` collections without an explicit default discriminator fall back to the first declared `[PolymorphicOption]`, the empty and `null` encoding here is internally consistent.
- Assuming the library wants `Serialize(Stream)` to work on any writable stream when the count is already known in memory, the seekability check above is a real behavior gap rather than just an optimization miss.
- This review is based on source inspection only. I did not run generator or behavioral tests because the task restricted writes to the report file.
