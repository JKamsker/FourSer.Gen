# PolymorphicCollectionImmutableQueue Review

## Verdict
Partially correct. The generated code should round-trip homogeneous `ImmutableQueue<IItem>` contents and preserve queue order, but it is not fully aligned with the declared `TypeIdProperty` contract or likely user expectations. `Inventory.ItemType` is never consulted during serialization; instead the serializer derives the discriminator from `Items` and falls back to `10` for empty or `null` queues (`tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImmutableQueue/input.cs:8-16`, `tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImmutableQueue/PolymorphicCollectionImmutableQueue.RunGeneratorTest.verified.txt:163-223`, `tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImmutableQueue/PolymorphicCollectionImmutableQueue.RunGeneratorTest.verified.txt:290-349`). That matches current checked-in tests, but it is surprising relative to the contract comments (`src/FourSer.Contracts/PolymorphicMode.cs:14`, `src/FourSer.Contracts/SerializeCollectionAttribute.cs:39`). No other material correctness issue stood out in the immutable-queue handling itself.

## Findings
1. Medium: `TypeIdProperty` is effectively ignored on serialize. The generated deserialize path reads the wire `itemType` and assigns `Inventory.ItemType` (`tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImmutableQueue/PolymorphicCollectionImmutableQueue.RunGeneratorTest.verified.txt:56-59`, `tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImmutableQueue/PolymorphicCollectionImmutableQueue.RunGeneratorTest.verified.txt:66-105`, `tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImmutableQueue/PolymorphicCollectionImmutableQueue.RunGeneratorTest.verified.txt:114-153`), but both serialize paths ignore `obj.ItemType`; they materialize `Items`, infer the discriminator from the first item, and hard-code `10` when the queue is empty or `null` (`tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImmutableQueue/PolymorphicCollectionImmutableQueue.RunGeneratorTest.verified.txt:163-223`, `tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImmutableQueue/PolymorphicCollectionImmutableQueue.RunGeneratorTest.verified.txt:290-349`). For example, `new Inventory { ItemType = 20, Items = ImmutableQueue<IItem>.Empty }` would serialize as type id `10` and round-trip back with `ItemType = 10`. Given `TypeIdProperty = nameof(ItemType)` in `tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImmutableQueue/input.cs:12` and the contract wording in `src/FourSer.Contracts/PolymorphicMode.cs:14` / `src/FourSer.Contracts/SerializeCollectionAttribute.cs:39`, this does not match likely user expectations, even though current tests explicitly codify the same behavior (`tests/FourSer.Tests/GeneratorTests.cs:240-275`, `tests/FourSer.Tests.Behavioural/Polymorphism/PolymorphicCollectionParityTests.cs:350-410`, `tests/FourSer.Tests.Behavioural/UseCases/SingleTypeIdTests.cs:42-96`).
2. Low: Each serialize path re-traverses the same buffered list multiple times and repeats the same discriminator switch three times. After `ToList(obj.Items)` (`tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImmutableQueue/PolymorphicCollectionImmutableQueue.RunGeneratorTest.verified.txt:163`, `tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImmutableQueue/PolymorphicCollectionImmutableQueue.RunGeneratorTest.verified.txt:290`), the code does a validation pass (`tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImmutableQueue/PolymorphicCollectionImmutableQueue.RunGeneratorTest.verified.txt:164-200`, `tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImmutableQueue/PolymorphicCollectionImmutableQueue.RunGeneratorTest.verified.txt:291-327`), a separate first-item pass to write the type id (`tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImmutableQueue/PolymorphicCollectionImmutableQueue.RunGeneratorTest.verified.txt:202-223`, `tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImmutableQueue/PolymorphicCollectionImmutableQueue.RunGeneratorTest.verified.txt:329-349`), and another first-item pass before the type-specific write switch (`tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImmutableQueue/PolymorphicCollectionImmutableQueue.RunGeneratorTest.verified.txt:230-274`, `tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImmutableQueue/PolymorphicCollectionImmutableQueue.RunGeneratorTest.verified.txt:357-400`). This is duplicate generated code and unnecessary CPU work for data that has already been materialized.
3. Info: The `Sword`, `Shield`, and `Potion` serializers are identical zero-member boilerplate, and each repeats its own `using` / alias prologue (`tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImmutableQueue/PolymorphicCollectionImmutableQueue.RunGeneratorTest.verified.txt:408-479`, `tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImmutableQueue/PolymorphicCollectionImmutableQueue.RunGeneratorTest.verified.txt:482-553`, `tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImmutableQueue/PolymorphicCollectionImmutableQueue.RunGeneratorTest.verified.txt:556-627`). That is not a behavior bug, but it is redundant generated output.

## Performance opportunities
- Cache `count` and validated `discriminator` from the first pass and reuse them instead of calling `Count()` and reopening enumerators later (`tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImmutableQueue/PolymorphicCollectionImmutableQueue.RunGeneratorTest.verified.txt:163-231`, `tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImmutableQueue/PolymorphicCollectionImmutableQueue.RunGeneratorTest.verified.txt:290-358`). Because `itemsValidatedItems` is already a `List<IItem>`, use `.Count` instead of LINQ `.Count()` at `tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImmutableQueue/PolymorphicCollectionImmutableQueue.RunGeneratorTest.verified.txt:164`, `tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImmutableQueue/PolymorphicCollectionImmutableQueue.RunGeneratorTest.verified.txt:202`, `tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImmutableQueue/PolymorphicCollectionImmutableQueue.RunGeneratorTest.verified.txt:230-231`, `tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImmutableQueue/PolymorphicCollectionImmutableQueue.RunGeneratorTest.verified.txt:291`, `tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImmutableQueue/PolymorphicCollectionImmutableQueue.RunGeneratorTest.verified.txt:329`, and `tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImmutableQueue/PolymorphicCollectionImmutableQueue.RunGeneratorTest.verified.txt:357-358`.
- There is no meaningful stream batching opportunity inside the item loop in this specific case because `Sword.Serialize(stream)`, `Shield.Serialize(stream)`, and `Potion.Serialize(stream)` are zero-byte no-ops (`tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImmutableQueue/PolymorphicCollectionImmutableQueue.RunGeneratorTest.verified.txt:472-478`, `tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImmutableQueue/PolymorphicCollectionImmutableQueue.RunGeneratorTest.verified.txt:546-552`, `tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImmutableQueue/PolymorphicCollectionImmutableQueue.RunGeneratorTest.verified.txt:620-626`). The real wins here are reducing list traversals and duplicate discriminator work, not additional IO coalescing.
- If the generator can recognize zero-payload homogeneous leaf types, it could skip the per-item serialize loops entirely after validation because the switch cases at `tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImmutableQueue/PolymorphicCollectionImmutableQueue.RunGeneratorTest.verified.txt:248-269` and `tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImmutableQueue/PolymorphicCollectionImmutableQueue.RunGeneratorTest.verified.txt:375-396` currently do CPU work without emitting any item bytes.
