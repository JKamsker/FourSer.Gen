# PolymorphicCollectionImmutableStack Review

## Verdict
Functionally correct for `tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImmutableStack/input.cs` and broadly aligned with likely user expectations for an `ImmutableStack<IItem>` using `PolymorphicMode.IndividualTypeIds`. The generated code preserves stack enumeration order by reading into a staging collection and reconstructing with `ImmutableStack.CreateRange(Reverse(...))`, which matches the generator's explicit `ImmutableStack` special case in `src/FourSer.Gen/CodeGenerators/Core/CollectionUtilities.cs:103-113`. No material correctness findings found.

## Findings
1. Low: Both serialize paths traverse `Items` redundantly. Each path does a full pre-validation pass, then a separate LINQ `Count()` pass, then the actual write loop, even though the later `switch` already contains `case null` / `default` guards. For `ImmutableStack<T>`, `Count()` is not backed by a count property, so this is another enumeration rather than an O(1) lookup (`tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImmutableStack/PolymorphicCollectionImmutableStack.RunGeneratorTest.verified.txt:134-177`, `tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImmutableStack/PolymorphicCollectionImmutableStack.RunGeneratorTest.verified.txt:193-236`, `src/FourSer.Gen/TypeInfoProvider.cs:545-557`).
2. Low: The source member is non-nullable, but the generated serializer still accepts `null` and canonicalizes it to an empty stack on the wire. `input.cs` declares `ImmutableStack<IItem> Items` without `?`, yet the serializer writes count `0` for `null` and deserialization always reconstructs a non-null `ImmutableStack<IItem>` (`tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImmutableStack/input.cs:8-12`, `tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImmutableStack/PolymorphicCollectionImmutableStack.RunGeneratorTest.verified.txt:83-84`, `tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImmutableStack/PolymorphicCollectionImmutableStack.RunGeneratorTest.verified.txt:123-124`, `tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImmutableStack/PolymorphicCollectionImmutableStack.RunGeneratorTest.verified.txt:144-147`, `tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImmutableStack/PolymorphicCollectionImmutableStack.RunGeneratorTest.verified.txt:203-206`). This is consistent with current generator metadata (`src/FourSer.Gen/TypeInfoProvider.cs:545-557`) but may still surprise users reading the source model.
3. Info: The generated output contains avoidable redundancy. The `case null` arms in both serializer `switch` statements are dead immediately after the upfront null-validation loops, the same polymorphic type map is re-emitted across sizing, both deserializers, and both serializers, and the three empty leaf serializers repeat near-identical boilerplate (`tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImmutableStack/PolymorphicCollectionImmutableStack.RunGeneratorTest.verified.txt:38`, `tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImmutableStack/PolymorphicCollectionImmutableStack.RunGeneratorTest.verified.txt:61-79`, `tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImmutableStack/PolymorphicCollectionImmutableStack.RunGeneratorTest.verified.txt:101-119`, `tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImmutableStack/PolymorphicCollectionImmutableStack.RunGeneratorTest.verified.txt:153-176`, `tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImmutableStack/PolymorphicCollectionImmutableStack.RunGeneratorTest.verified.txt:212-235`, `tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImmutableStack/PolymorphicCollectionImmutableStack.RunGeneratorTest.verified.txt:243-462`).

## Performance opportunities
- If the generator keeps this collection shape allocation-free, the serializer should still avoid the current three-pass pattern over `ImmutableStack<T>`. A single staging/materialization pass or a combined validation-and-count pass would remove redundant traversal before writing (`tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImmutableStack/PolymorphicCollectionImmutableStack.RunGeneratorTest.verified.txt:134-177`, `tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImmutableStack/PolymorphicCollectionImmutableStack.RunGeneratorTest.verified.txt:193-236`).
- The stream serializer currently performs one `StreamWriter.WriteByte` call per item discriminator. In this fixture the leaf serializers are empty, so the payload after the count is just discriminator bytes; batching those bytes into a span and using `StreamWriter.WriteBytes` would reduce stream call count for large collections (`tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImmutableStack/PolymorphicCollectionImmutableStack.RunGeneratorTest.verified.txt:209-229`, `src/FourSer.Gen/Resources/Code/StreamWriterHelpers.cs:15-17`, `src/FourSer.Gen/Resources/Code/StreamWriterHelpers.cs:33-36`).
- Deserialization currently uses `List<IItem>` plus `Enumerable.Reverse(...)` before `ImmutableStack.CreateRange(...)`. Because the count is known up front, a pre-sized array filled from the end could remove the extra reverse iterator layer while preserving observable stack order (`tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImmutableStack/PolymorphicCollectionImmutableStack.RunGeneratorTest.verified.txt:55-84`, `tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImmutableStack/PolymorphicCollectionImmutableStack.RunGeneratorTest.verified.txt:95-124`, `src/FourSer.Gen/CodeGenerators/Core/CollectionUtilities.cs:108-110`).

## Open questions / assumptions
- Assuming the current contract intentionally treats `null` and empty immutable collections the same on the wire, the generated null-handling is acceptable even though the source member is non-nullable.
- Assuming expected `ImmutableStack<T>` behavior is preservation of observable enumeration order rather than preserving internal node identity, this case is correct. The repo's parity tests clearly expect immutable polymorphic stacks to round-trip as sequences (`tests/FourSer.Tests.Behavioural/Polymorphism/PolymorphicCollectionParityTests.cs:217-271`).
- A targeted local `dotnet test` run could not execute because this machine is missing `Microsoft.NETCore.App 9.0.0`. The verdict is therefore based on static inspection plus a direct runtime sanity check of `ImmutableStack<T>` enumeration and `CreateRange(Reverse(...))` semantics, not on a completed local test run.
