# PolymorphicCollectionImplicitMode Review

## Verdict
Mostly correct for the generator's current internal model: `TypeIdProperty` implicitly selects `SingleTypeId`, and the snapshot round-trips its own wire format by reading `TypeId` first and then deserializing a homogeneous `Items` collection from that discriminator (`src/FourSer.Gen/TypeInfoProvider.cs:1276-1282`, `tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImplicitMode/PolymorphicCollectionImplicitMode.RunGeneratorTest.verified.txt:66-107`, `tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImplicitMode/PolymorphicCollectionImplicitMode.RunGeneratorTest.verified.txt:116-157`). It does not fully match likely user expectations, though, because the generated serializer treats `Inventory.TypeId` as a derived output from `Items` rather than an input to serialization.

## Findings
1. Medium: The generated serializer ignores `Inventory.TypeId` as the source of truth and derives the serialized discriminator from `Items` instead. `tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImplicitMode/input.cs:10-16` declares a separate `TypeId` member and points the collection at it with `[SerializeCollection(TypeIdProperty = nameof(TypeId))]`. The public contract also describes `TypeIdProperty` as the property that "holds the TypeId for all elements in the collection" and shows it as what "determines the type for all entities" (`src/FourSer.Contracts/SerializeCollectionAttribute.cs:36-39`, `README.md:287-292`); the implementation guide likewise says `SingleTypeId` serialization should read the type id from that property and write it once (`docs/polymorphic_collections_implementation_guide.md:163-167`). In the snapshot, however, both serializers ignore `obj.TypeId`: they write `10` for empty or `null` collections (`tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImplicitMode/PolymorphicCollectionImplicitMode.RunGeneratorTest.verified.txt:200-203`, `tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImplicitMode/PolymorphicCollectionImplicitMode.RunGeneratorTest.verified.txt:311-314`) and otherwise recompute the discriminator from `obj.Items[0]` (`tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImplicitMode/PolymorphicCollectionImplicitMode.RunGeneratorTest.verified.txt:206-215`, `tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImplicitMode/PolymorphicCollectionImplicitMode.RunGeneratorTest.verified.txt:317-326`). That means `TypeId = 20` with an empty list still serializes as `10`, and a mismatched `TypeId` is silently ignored rather than validated.
2. Low: The non-nullable `Items` member is treated as optional and normalized on deserialize. `tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImplicitMode/input.cs:16` declares `List<Item> Items` without `?`, but the serializers accept `null`, emit the same wire shape as an empty list (`tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImplicitMode/PolymorphicCollectionImplicitMode.RunGeneratorTest.verified.txt:200-203`, `tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImplicitMode/PolymorphicCollectionImplicitMode.RunGeneratorTest.verified.txt:217-220`, `tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImplicitMode/PolymorphicCollectionImplicitMode.RunGeneratorTest.verified.txt:311-314`, `tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImplicitMode/PolymorphicCollectionImplicitMode.RunGeneratorTest.verified.txt:328-331`), and deserialize back to a non-null `List<Item>` every time (`tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImplicitMode/PolymorphicCollectionImplicitMode.RunGeneratorTest.verified.txt:69-75`, `tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImplicitMode/PolymorphicCollectionImplicitMode.RunGeneratorTest.verified.txt:119-125`). That is internally consistent, but it is still a likely surprise from the source model.
3. Info: The snapshot contains a fair amount of redundant generated code. The same collection validation and discriminator resolution logic is emitted in both serializers and then recomputed again for the actual write/switch (`tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImplicitMode/PolymorphicCollectionImplicitMode.RunGeneratorTest.verified.txt:167-198`, `tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImplicitMode/PolymorphicCollectionImplicitMode.RunGeneratorTest.verified.txt:206-234`, `tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImplicitMode/PolymorphicCollectionImplicitMode.RunGeneratorTest.verified.txt:278-309`, `tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImplicitMode/PolymorphicCollectionImplicitMode.RunGeneratorTest.verified.txt:317-345`). The concatenated output also repeats identical `using` blocks and nearly identical zero-member serializers for `Item`, `Sword`, `Shield`, and `Potion` (`tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImplicitMode/PolymorphicCollectionImplicitMode.RunGeneratorTest.verified.txt:380-673`).

## Performance opportunities
- No meaningful stream batching win exists in this exact snapshot because `Sword`, `Shield`, and `Potion` serialize no payload bytes; the stream path already performs only the scalar `TypeId` and count writes for `Inventory`, and the per-item loops are effectively CPU-only (`tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImplicitMode/PolymorphicCollectionImplicitMode.RunGeneratorTest.verified.txt:313-330`, `tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImplicitMode/PolymorphicCollectionImplicitMode.RunGeneratorTest.verified.txt:349-368`).
- Reuse the first-pass `validatedDiscriminator` for the actual `TypeId` write and collection switch instead of recomputing it from `obj.Items[0]` twice in each serializer (`tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImplicitMode/PolymorphicCollectionImplicitMode.RunGeneratorTest.verified.txt:174-196`, `tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImplicitMode/PolymorphicCollectionImplicitMode.RunGeneratorTest.verified.txt:206-234`, `tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImplicitMode/PolymorphicCollectionImplicitMode.RunGeneratorTest.verified.txt:285-307`, `tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImplicitMode/PolymorphicCollectionImplicitMode.RunGeneratorTest.verified.txt:317-345`).
- `GetPacketSize` performs another full discriminator-validation pass over the same list, so sizing plus serialization currently re-walks the collection multiple times (`tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImplicitMode/PolymorphicCollectionImplicitMode.RunGeneratorTest.verified.txt:30-51`, `tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImplicitMode/PolymorphicCollectionImplicitMode.RunGeneratorTest.verified.txt:167-198`, `tests/FourSer.Tests/GeneratorTestCases/PolymorphicCollectionImplicitMode/PolymorphicCollectionImplicitMode.RunGeneratorTest.verified.txt:278-309`).

## Open questions / assumptions
- This review assumes the attribute/docs wording is the intended contract for `TypeIdProperty`. If the intended behavior is instead "derive the discriminator from the collection and only surface it through the property on deserialize", then the first finding is primarily a documentation and expectation mismatch rather than a serializer defect.
- Static review only. I did not run generator or behavioral tests because the task was limited to producing the report without making other code changes.
