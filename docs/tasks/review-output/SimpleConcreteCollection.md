# SimpleConcreteCollection Review

## Verdict
Functionally correct for FourSer's current collection and string contracts. The generated code correctly serializes `SimpleConcreteCollectionTest.Cats` as a count-prefixed `List<Cat>`, includes the inherited `Animal.Id` in `Cat`, rejects `null` collection items, and round-trips back to a concrete list. No material functional bug found.

The main expectation mismatch is that the generated code is looser than the source nullability contracts for both `Cats` and `Cat.Name`.

## Findings

Both deserializers always materialize a non-null `List<Cat>` in `tests/FourSer.Tests/GeneratorTestCases/SimpleConcreteCollection/SimpleConcreteCollection.RunGeneratorTest.verified.txt:54-63` and `tests/FourSer.Tests/GeneratorTestCases/SimpleConcreteCollection/SimpleConcreteCollection.RunGeneratorTest.verified.txt:73-82`. This matches the current collection behavior covered in `tests/FourSer.Tests.Behavioural/Collections/CollectionTests.cs:97-109`, `tests/FourSer.Tests/OptimizationCollectionFailureTests.cs:101-145`, and the generator metadata in `src/FourSer.Gen/TypeInfoProvider.cs:239-250`, so it is not a functional regression, but it is likely surprising to a user reading the source model.

## Performance opportunities
- No major collection-level batching gap is obvious for the span path. `Cats` contains reference-type elements with variable-size `string` payloads, so the unmanaged bulk collection fast path does not apply here.
- Stream collection IO is still per element. `SimpleConcreteCollectionTest.Serialize(obj, stream)` delegates once per cat in `tests/FourSer.Tests/GeneratorTestCases/SimpleConcreteCollection/SimpleConcreteCollection.RunGeneratorTest.verified.txt:126-133`, and each `Cat` stream serializer writes `Id` separately from the buffered string payload in `tests/FourSer.Tests/GeneratorTestCases/SimpleConcreteCollection/SimpleConcreteCollection.RunGeneratorTest.verified.txt:228-242`. A future buffered object or collection path could reduce stream writes.
- Stream deserialization is also per element and per field. `SimpleConcreteCollectionTest.Deserialize(stream)` calls `Cat.Deserialize(stream)` once per item in `tests/FourSer.Tests/GeneratorTestCases/SimpleConcreteCollection/SimpleConcreteCollection.RunGeneratorTest.verified.txt:76-78`, and each `Cat` then reads `Id` and the string separately in `tests/FourSer.Tests/GeneratorTestCases/SimpleConcreteCollection/SimpleConcreteCollection.RunGeneratorTest.verified.txt:201-202`. Reading the fixed-width prefix (`Id` plus string length) together before the UTF-8 payload would cut one stream read per element.
- The collection loops perform duplicate null guards before calling nested serializer methods. `SimpleConcreteCollectionTest` checks each item for `null` in `tests/FourSer.Tests/GeneratorTestCases/SimpleConcreteCollection/SimpleConcreteCollection.RunGeneratorTest.verified.txt:31-37`, `tests/FourSer.Tests/GeneratorTestCases/SimpleConcreteCollection/SimpleConcreteCollection.RunGeneratorTest.verified.txt:100-104`, and `tests/FourSer.Tests/GeneratorTestCases/SimpleConcreteCollection/SimpleConcreteCollection.RunGeneratorTest.verified.txt:129-133`, then `Cat.GetPacketSize` / `Cat.Serialize` immediately check `obj is null` again in `tests/FourSer.Tests/GeneratorTestCases/SimpleConcreteCollection/SimpleConcreteCollection.RunGeneratorTest.verified.txt:160-165`, `tests/FourSer.Tests/GeneratorTestCases/SimpleConcreteCollection/SimpleConcreteCollection.RunGeneratorTest.verified.txt:209-212`, and `tests/FourSer.Tests/GeneratorTestCases/SimpleConcreteCollection/SimpleConcreteCollection.RunGeneratorTest.verified.txt:224-227`. A trusted non-null internal path would remove one branch per element.
- The list deserializers preallocate capacity but still use `.Add(...)` for each item in `tests/FourSer.Tests/GeneratorTestCases/SimpleConcreteCollection/SimpleConcreteCollection.RunGeneratorTest.verified.txt:56-60` and `tests/FourSer.Tests/GeneratorTestCases/SimpleConcreteCollection/SimpleConcreteCollection.RunGeneratorTest.verified.txt:75-79`. If the generator ever uses `CollectionsMarshal.SetCount` for reference-type lists too, it could assign by index and skip repeated list bookkeeping.

## Open questions / assumptions
- Assuming the intended contract for dynamic-count collections is "serialize `null` as zero count and deserialize zero count as an empty concrete collection," the generated `Cats` handling is correct.
- Assuming the repo-wide string contract is "zero-length on the wire maps to `string.Empty`, and `null` is treated the same as empty when writing," the generated `Cat.Name` handling is also correct.
- A targeted `dotnet test --filter "DisplayName~SimpleConcreteCollection"` run could not complete locally because `Microsoft.NETCore.App 9.0.0` is not installed on this machine, so the review is based on source inspection and surrounding behavioral tests.
